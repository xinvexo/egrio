# 待办与已知问题

本页是唯一的待办清单：未完成的工作、已知缺陷与未验证范围。每项写明问题、影响与完成标准；完成后
直接删除该项。

## 依赖安全

### DNS 报文编码的 CPU 耗尽风险

[Cargo.lock](../Cargo.lock) 锁定的 `hickory-proto 0.25.2` 受
[RUSTSEC-2026-0119](https://rustsec.org/advisories/RUSTSEC-2026-0119.html) 影响：报文编码中的名称压缩可能导致 CPU 耗尽。
生产 [DNS 编码入口](../crates/egrio-core/src/dns/wire.rs) 调用 `Message::to_vec()`；外部输入在当前配置下能否触发该问题
尚未验证。完成标准：升级到至少 `0.26.1`、适配接口并通过 DNS 回归测试。

同库的 [RUSTSEC-2026-0118](https://rustsec.org/advisories/RUSTSEC-2026-0118.html) 要求启用 DNSSEC feature 并执行 NSEC3 验证；
[Core 依赖声明](../crates/egrio-core/Cargo.toml) 关闭默认 feature、仅启用 `std`，当前未启用该触发路径。

### 可选 Go 互通工具的加密依赖告警

`scripts/validation/ss2022-peer` 的 [依赖声明](../scripts/validation/ss2022-peer/go.mod) 与
[校验清单](../scripts/validation/ss2022-peer/go.sum) 固定了存在安全告警的 `golang.org/x/crypto v0.23.0`。
该工具不进入发行包，实际导入图不包含 `ssh`，告警的适用性须按所用包与调用路径判断。完成标准：在受支持的 Go 工具链下
升级依赖，覆盖适用的安全修复，并保留工具及显式的 Shadowsocks 2022 互通测试。

## Windows

### Wintun 唤醒竞争

服务在每个突发结束后发送一个被丢弃的 IPv4 头，绕过 Wintun 0.14.1 发送路径的唤醒竞争（见
[Windows 特权服务](platforms/windows.md#特权服务)）。完成标准：Wintun 发布包含上游 ec0a6b98 的官方签名
版本后，升级 `wintun.dll` 并去掉唤醒包。

## Core 执行线程

### 单队列捕获的多流峰值

Wintun 与 utun 各只有一个捕获队列、一个执行器（Linux 多队列 TUN 见
[Core](architecture/core.md#包设备与包泵)）。单队列执行器可能限制高吞吐多流的峰值；把 relay 放到其他执行器虽然能
抬高部分平台的峰值，也会增加跨线程交接与每字节 CPU，部分平台的上传性能还会下降，因而不作为默认路径。

有千兆以上多流峰值需求时，可按流表把捕获包分到各执行器的虚拟队列，各执行器保有自己的流与发送队列；新流只在
现有执行器跑满时才交给其他队列。macOS 由首个包泵转交其他队列的包，Windows 可由服务按流表分发到各执行器的一对
共享环。实现前按 XNU utun 与 Wintun 的头文件核对多线程读写约束。完成标准：多流峰值接近按核数配置工作线程时的
水平，单流与常见链路速率下的每字节 CPU 不变差。

## OpenVPN 出站

### 未实现的现代特性

tls-crypt-v2、服务器推迟认证（`AUTH_PENDING` 与网页认证）和挑战应答（CRV1）的二次验证、2.6 的动态 tls-crypt（重新协商用导出器
派生的控制通道密钥）、2.7 的 epoch 数据密钥都未实现（见 [Core 架构](architecture/core.md) 的 `protocols/openvpn/`）；用这些特性的
服务器连不上或退回旧做法。完成标准：按需实现，每项有进程内服务器的测试，并对一台用到它的真实服务器验证。

## 路由排除与全局模式

### 系统验证

三个平台都已验证全局模式物理网卡抓包与 STUN（严格全局模式下 Trojan、Hysteria2、Shadowsocks 与 SOCKS5
节点都收发 UDP），Windows 与 Linux 已验证排除与原地更新，Linux 另验证入站回包，macOS 与 Windows 另验证经移动
网络的真实远程桌面会话（两者都含全局模式，见各平台的验证状态），macOS 另验证了有线与 Wi-Fi 之间换上行时
排除跟随新的主服务。未验证：Linux 上来自非 LAN 地址的真实远程桌面会话，以及 Linux 上全局模式下的远程桌面会话。
完成标准：在支持公网入站的测试网络上按 Linux 验收 runbook 通过并写入验证状态。

## TUN 与 fake IP

### macOS 软件包下载的间歇性慢速

Homebrew 与系统更新有开启 TUN 后大文件下载缓慢、间歇停顿的反馈。按软件包 URL 与 curl 请求方式复现了单流降速，
其中一轮已结合节点发送状态定位到节点至本机的 TCP 传输，尚无 Egrio 内部限速或并发阻断的证据，详见
[下载与并发验证](platforms/macos.md#大文件下载与并发)。实际系统更新任务、IPv6 与后台下载优先级仍需覆盖。
完成标准：在实际慢速任务中取得具体 URL、CDN 地址、地址族与出站，保持这些条件与读取方式一致，交替比较物理旁路、
混合代理和 TUN 的逐秒字节数与停顿，结合上游收包、窗口及重传定位原因；若为 Core 缺陷，补可重复的回归并修复。

### 上游的 fake IP 与本机地址池同段

上游解析器返回的 fake IP 与本机池同段时，Core 自己拨号得到的也可能是池内地址。macOS 物理接口上的拒绝路由
（见[网络设置](platforms/macos.md#网络设置与捕获范围)）会拒绝这样的拨号。Core 丢弃落在本机池内的上游答复，
改问配置写明的服务器（见[Core 架构](architecture/core.md#模块布局)）；若备用来源同样被 UDP/53 劫持，仍无法得到
真实地址，需要不经 53 端口的解析来源或不同网段的池。macOS 已核对数值地址 DoH 的情形，见
[验证状态](platforms/macos.md#验证状态)。完成标准：Windows 与 Linux 按 runbook 核对相同条件；两者没有 macOS 的
物理接口拒绝路由，需分别确认结果。

## 规则集

### 规则集下载不到时无法首次启动

Core 启动前先下载规则实际引用的规则集，缺一份就不启动（见
[来源解析与生效](architecture/profile-store.md#来源解析与生效)）。下载走系统此刻的出口：系统代理开着时经它，否则直连
（`remote_fetch_client`）。所以在没有任何代理在运行的机器上，规则集又放在直连到不了的主机时，启动因规则集缺失被拒绝，
而能下载到它的那条路正是还没启动的 Core；此时只能把配置里的地址换成直连可达的，或去掉引用它的规则。这条路径没有在
这样的网络里实测过，只按代码与 reqwest 的系统代理行为推得。完成标准：直连失败后改经配置里的节点下载——一个只带节点、
规则只有一条兜底的一次性 Core 监听器，出口取全局出口的选择，没有选择时取配置的第一个策略组——并在一台直连到不了
规则集主机、没有其他代理的机器上首次启动成功；缺失的规则集仍不交给 Core 跳过。

## 桌面界面

### 恢复不了上次会话时无法启动

启动先恢复上一个进程留下的 checkpoint，失败就说明原因并退出（见[启动](architecture/desktop.md#启动)）。TUN 的
checkpoint 要经特权服务恢复（`egrio-service` 的 `remote.rs` 向服务发 `Restore`），所以开着 TUN 时崩溃或断电之后，
只要服务连不上——被停用、被卸载、macOS 上后台项目的许可被收回——应用每次启动都在这一步退出，而重新安装或
重新允许服务的入口正在应用里；重启后隧道的系统状态本来已经不在。完成标准：恢复失败时应用照常启动，checkpoint
与租约留在 `RecoveryRequired`，消息里记一条恢复失败及原因，之后每次开启捕获层先重试恢复（`desktop_runtime` 已经
先调用 `initialize`），恢复成功前不开启任何层；在三个平台上以“留着 TUN checkpoint、服务不可达”启动核对。


### macOS 应用的开机启动

macOS 的开机启动改用应用自己的登录项（`SMAppService.mainAppService`）；登记、撤销与登录后由系统启动（静默启动时
不开主窗口）已在 macOS 13.6 虚拟机上验证，macOS 实体环境上还没有。完成标准：签名的应用包在 macOS 实体环境上登录后启动，
静默启动打开时不显示主窗口，并写入 macOS 的验证状态。

### macOS 服务换签名类别后的恢复

已获允许的服务换成签名类别不同的包后（Apple Development 与 Developer ID 之间，见
[macOS 平台](platforms/macos.md#产品身份签名与服务安装)），launchd 拒绝启动、系统要求重新批准，被拒的任务仍载入在
launchd 里。桌面开启 TUN 时只再注册，卸不下这个任务；批准后系统会不会换掉它没有验证，现在要手动注销再注册。
完成标准：在 macOS 实体环境上从已允许的开发签名服务换成 Developer ID 包，开启 TUN 并批准一次即可用；不行就由桌面在另一个
进程里注销再注册。

### 节点页的键盘操作

macOS 上节点页的磁贴不能用 Tab 聚焦，也不能用空格或回车按下，只能用指针或辅助功能的按下（VoiceOver）。完成标准：
磁贴可以用键盘移动焦点并按下，焦点环用系统样式，移动焦点本身不触发按下；依据 `NSCollectionView` 的键盘导航实现。

### 对话框里的错误移动字段

添加配置的对话框在说明文字的位置给出失败原因，规则对话框在按钮行里给出；原因与说明的行数不同时，下面的字段
跟着上移或下移，违背界面不因改动移位的规则。完成
标准：界面层有一个只显示其中一层、却按最高一层占位的组件（GTK 的同质 `GtkStack`、WinUI 同一格里不透明度为 0
的层、AppKit 隐藏但仍参与约束的子视图），说明与原因放在同一个位置，原因不比说明长时字段不动；三个平台截图核对。

### 消息胶囊的悬停

面板收起时指针下的胶囊底色加深、打开的面板的抬头不显底色，三个平台的真实指针验证尚未完成。控制口与
无头环境不能代替该验收。完成标准：在三个平台上以真实的
指针移动验证悬停底色，以及点按打开后指针仍停在抬头上时抬头不显底色，写入各平台的验证状态。

### 托盘按组生成后的验证

托盘的策略组按组描述、成员行在显示时才做（见[桌面架构](architecture/desktop.md#托盘)）。macOS 27.2 已运行
验证；Windows 与 Linux 的菜单构造测试已通过（见两个平台文档的托盘一项）。没有验证的：
- macOS 13.6：子菜单的 `menuNeedsUpdate:` 是不是在它将要展开时才到。如果旧的菜单实现在托盘菜单打开时就向全部
  子菜单要内容，订阅规模的配置第一次打开托盘时会做出全部的行，没展开过的组的行一直留着。
- Windows 与 Linux：改后的菜单没有在桌面上真的打开过（组的测速、选成员、延迟的更新）。
- Linux 在订阅规模下的代价没有量过：每次更新 ksni 按描述重建整棵菜单并比较，宿主（GNOME 的 AppIndicator 扩展）
  取整棵 dbusmenu 布局；ksni 0.3.7 不支持子菜单的 `AboutToShow`，做不到按需给成员。虚拟机里没有显示托盘的宿主，
  要在带托盘宿主的 GNOME 桌面会话里测量。

完成标准：三个平台都在实际桌面会话里打开托盘菜单核对，Linux 用 300 个节点、18 个组的配置量出更新与打开的耗时；结果
写入各平台的验证状态，量出问题的另立一项。

### Windows 界面的余项

Windows 界面尚需处理以下平台差异：
- 窗口的默认与最小尺寸按打开时主显示器的缩放算，不随显示器变化（`hwnd::scale` 与 `XamlRoot.Changed` 才对）。
- 滚动条这类接住按下又不取焦点的控件，点按它时消息面板不收起（要 `AddHandler(PointerPressedEvent, …, true)`，
  生成的绑定里委托不能从外部构造）。
- 浮出控件与提示框不跟随固定的浅色或深色；提示框的延迟未核对；不能按的磁贴仍有悬停与按下效果，需以真实指针核对。
- 上一个对话框还在关闭时打开新的未核对；5000 行时重建单元格的开销未核对。
完成标准：逐项修好或在 Windows 平台文档里说明为平台差异，并在实体机上核对。

### Linux 界面的余项

Linux 界面尚需处理以下平台差异：控制口缺按坐标点按、输入法组字、托盘菜单的
打开与关闭（GTK 不收合成输入，SNI 的菜单由面板打开）；托盘图标是全彩的而 GNOME 面板要符号图标；行的拖动来源与
落点按单元格，单元格之间的空隙不能开始拖动、落点线有缺口，靠边自动滚动未核对；`AdwDialog` 连标题栏一起变暗，
点按变暗处是否发出关闭请求未核对；编辑器窗口不能居中在主窗口上（Wayland 的限制，见 `editor.rs`）。完成标准：
逐项修好或在 Linux 平台文档里说明为平台差异，并在 Ubuntu 上核对。

### 完整的代码编辑器

编辑器窗口是纯文本框（见[编辑器窗口](architecture/desktop.md#编辑器窗口)），没有语法高亮、按 Clash 字段的补全与
悬停说明、不支持字段的标记、行号、缩进参考线、列表续行与格式化。完成标准：另写设计后实现，分词、补全与诊断放在
共享的 Rust 里，各平台只承载原生文本视图。

### 发行包的系统验证

`cargo xtask package` 在三个平台生成发布的安装包（见[发布](runbooks/release.md)），这些还没有验证：
- 发布工作流还没在 GitHub 上运行过：配好 secrets 后推送一个版本的标签，四个打包作业与发布作业都成功，发布里有五个
  文件，旧版本的应用检查更新时找到它，升级后运行的是新版本。
- macOS：在 Apple 芯片上交叉编译的 Intel DMG 在 Intel Mac 上安装、启动，经安装的应用开启 TUN。
- Windows：没有 Windows App Runtime 的干净系统上安装（运行时安装程序真正装上运行时），经安装的应用开启 TUN。
- Linux：在 Ubuntu 24.04 与 26.04 的 GNOME 会话（Wayland）里装上 deb，应用网格与程序坞显示 Egrio 的图标、窗口归在它
  名下并能固定到程序坞；装着 deb 的桌面经包里的助手开启 TUN，关闭后卸载；从应用升级时 Ubuntu 的软件中心打开 deb
  并装上。

完成标准：逐项验证，结果写入各平台文档的验证状态。
